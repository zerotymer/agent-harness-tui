# Git 브랜치 가이드라인

## 사전 정의 변수

* `{DATE}`: 현재 날짜를 `YYYY-MM-DD` 형식으로 매핑한다.
* `{DATETIME}`: 현재 날짜와 시각을 `YYYYMMDD-HHmmss` 형식으로 매핑한다.
* `{UUID}`: UUIDv7 값의 앞 8자리를 사용한 짧은 UUID.
* `{UUIDv7}`: UUID v7 전체 값.
* `{NAME}`: 브랜치의 목적 또는 내용을 나타내는 설명형 명칭.

## 브랜치 이름 규칙

* 프로젝트 가독성 또는 업무 맥락상 필요한 경우 브랜치 이름에 한글을 사용할 수 있다.
* 가능한 한 단순하고 일관된 이름을 사용한다.
* 쉘, URL, CI/CD, 파일시스템에서 문제를 일으키기 쉬운 문자는 피한다.
* 공백은 사용하지 않는다. 대신 `-` 또는 `_`를 사용한다.
* `:`, `?`, `*`, `[`, `]`, `\`, 연속된 슬래시는 피한다.
* 브랜치 이름만 보고 작업 목적을 이해할 수 있을 정도로 설명적으로 작성한다.
* 이름 충돌 가능성이 있는 작업 브랜치에는 `{UUID}`를 추가한다.

## 브랜치 운용 원칙

* `main`, `staging`, `dev`는 보호 대상 기준 브랜치다.
* `main`, `staging`, `dev`는 일반 작업용 브랜치가 아니다.
* 이 브랜치들은 특정 환경의 배포 자동화와 연결될 수 있다.
* `main`과 `staging`에는 직접 커밋하지 않는다.
* `dev`에는 개발 서버 검증 목적의 제한적인 직접 커밋만 허용한다.
* 실제 작업은 `feature`, `fix`, `hotfix`, `temp`, `merge` 브랜치에서 수행한다.
* 보호 대상 기준 브랜치로 병합할 때는 Pull Request, Merge Request 또는 이에 준하는 명시적 검토 절차를 사용한다.
* 릴리스, 배포, 검증 마일스톤이 생성될 때 `main`과 `staging`에는 버전 태그를 부여한다.

## 브랜치 네이밍

### `main`

`main`: 최종 운영 가능 상태를 위한 브랜치.

* 임의로 병합하지 않는다.
* 직접 커밋하지 않는다.
* 특별한 사유가 없는 한 운영 릴리스의 기준 브랜치로 사용한다.
* 운영 릴리스 또는 운영 가능 마일스톤이 생성되면 버전 태그를 부여한다.

태그 예시:

```text
v1.0.0
v1.0.1
release-20260614
```

### `staging`

`staging`: 운영 반영 전 최종 테스트를 위한 검증 브랜치.

* 임의로 병합하지 않는다.
* 직접 커밋하지 않는다.
* 스테이징 서버 배포, 최종 QA, 릴리스 검증, 운영 전 점검에 사용한다.
* 스테이징 배포 또는 검증 마일스톤이 생성되면 버전 태그를 부여한다.

태그 예시:

```text
staging-v1.0.0
staging-20260614
rc-1.0.0
```

### `dev`

`dev`: 개발 서버 테스트를 위한 기준 브랜치.

* 임의로 병합하지 않는다.
* 직접 커밋은 제한적으로만 허용한다.
* 개발 서버 배포, 통합 테스트, 초기 검증에 사용한다.
* 개발 환경 배포 자동화와 연결될 수 있다.
* 개인 작업 브랜치처럼 사용하지 않는다.

### `feature`

`feature/{NAME}/{UUID}`: 기능 개발을 위한 브랜치.

* 주로 `main`에서 분기한다.
* 기능을 먼저 개발 환경 기준으로 검증해야 하는 경우 `dev`에서 분기할 수 있다.
* 기능 브랜치명이 중복되지 않도록 짧은 UUID를 추가한다.
* 프로젝트 릴리스 흐름에 따라 `dev`, `staging`, `main`으로 병합한다.

예시:

```text
feature/user-login/018fc2a1
feature/결제-세션-개선/018fc2a1
```

### `fix`

`fix/{NAME}/{UUID}`: 버그 수정 또는 관련 보정을 위한 브랜치.

* 주로 문제가 발생한 대상 브랜치에서 분기한다.
* 운영 버그는 별도 사유가 없는 한 `main`에서 분기한다.
* 스테이징에서만 발생한 문제는 `staging`에서 분기한다.
* 개발 서버에서만 발생한 문제는 `dev`에서 분기한다.

예시:

```text
fix/payment-callback/018fc2a1
fix/삼성브라우저-세션/018fc2a1
```

### `hotfix`

`hotfix/{NAME}/{UUID}`: 운영 긴급 수정을 위한 브랜치.

* `main`에서 분기한다.
* 운영 가능 브랜치를 기준으로 즉시 수정해야 하는 긴급 이슈에만 사용한다.
* `main`에 병합한 뒤, 필요한 경우 `staging`과 `dev`에도 역병합하거나 반영한다.
* 핫픽스가 운영에 반영되면 `main`에 버전 태그를 부여한다.
* 핫픽스를 스테이징에서도 검증한 경우 `staging`에도 버전 태그를 부여한다.

예시:

```text
hotfix/login-session-expiry/018fc2a1
hotfix/운영-결제오류/018fc2a1
```

### `temp`

`temp/{DATETIME}-{UUID}`: 임시 브랜치.

* 별도 대상 브랜치가 필요한 경우가 아니라면 주로 `main`에서 분기한다.
* 최종 작업 유형이 명확하지 않을 때 임시로 생성한다.
* 장기 브랜치로 취급하지 않는다.
* 최종 push 또는 검토 전에 적절한 `feature`, `fix`, `hotfix` 브랜치로 이름을 변경하거나 해당 브랜치에 병합한다.
* 작업이 재정리되거나 완료되면 삭제한다.

예시:

```text
temp/20260614-213045-018fc2a1
```

### `merge`

`merge/{NAME}/{UUID}`: 병합 검증을 위한 브랜치.

* 임시 병합 테스트에 사용한다.
* 충돌 확인, 통합 테스트, 변경사항 결합 검증을 실제 병합 전에 수행하기 위해 사용한다.
* 영구 통합 브랜치로 사용하지 않는다.
* 검토 절차나 보호 브랜치 규칙을 우회하기 위한 용도로 사용하지 않는다.
* `main`, `staging`, `dev`로의 실제 병합은 프로젝트의 검토 및 승인 절차를 따른다.

예시:

```text
merge/release-1.0.0/018fc2a1
merge/staging-validation/018fc2a1
```

## 권장 흐름

### 일반 기능 개발 흐름

```text
main
  └─ feature/{NAME}/{UUID}
       └─ dev
            └─ staging
                 └─ main
```

### 버그 수정 흐름

```text
target branch
  └─ fix/{NAME}/{UUID}
       └─ target branch
```

여기서 `target branch`는 `main`, `staging`, `dev` 중 하나일 수 있다.

### 운영 긴급 수정 흐름

```text
main
  └─ hotfix/{NAME}/{UUID}
       └─ main
       └─ staging
       └─ dev
```

### 임시 작업 흐름

```text
main
  └─ temp/{DATETIME}-{UUID}
       └─ feature/{NAME}/{UUID}
```

또는:

```text
main
  └─ temp/{DATETIME}-{UUID}
       └─ fix/{NAME}/{UUID}
```

## 태그 규칙

* 운영 릴리스 또는 운영 가능 마일스톤에는 `main`에 버전 태그를 부여한다.
* 스테이징 배포, 릴리스 후보, 검증 마일스톤에는 `staging`에 버전 태그를 부여한다.
* 배포된 태그는 변경하지 않는 것을 원칙으로 한다.
* 잘못된 태그를 생성한 경우, 프로젝트에서 명시적으로 태그 재작성 정책을 허용하지 않는 한 기존 태그를 조용히 이동하지 말고 수정된 새 태그를 생성한다.

권장 태그 예시:

```text
v1.0.0
v1.0.1
rc-1.0.0
staging-v1.0.0
release-20260614
```
