# 2단계: 카탈로그 연동

## 선행 조건 및 목표

[1단계](STEP_1_INITIAL_CREATION_ko.md) 완료 기준을 충족한 뒤 시작한다(2026-11-20 인수). 독립 실행형 TUI에 카탈로그 세 가지를 추가한다: Wiki.js 페이지, 공개 스킬, 문서. 사용자는 UUID나 설치 명령을 직접 입력하는 대신 카탈로그에서 항목을 고른다. 카탈로그 파일이 하나도 없어도 1단계 초기화는 그대로 동작해야 한다.

범위 제한 업데이터, override 계층, 모드, 훅, Git worktree, Worktrunk, Docktree는 [3단계](STEP_3_ADDITIONAL_FEATURES_ko.md)로 옮겼다. 이 지시서는 외부 서비스의 구축·배포를 지시하지 않는다.

## 1. 카탈로그 파일

- JSON 파일 세 개(`wiki.json`, `skills.json`, `docs.json`)가 같은 공통 틀을 쓴다. 형식은 [HARNESS_CATALOG_CONTRACT_ko.md](HARNESS_CATALOG_CONTRACT_ko.md)에 정의한다.
- 카탈로그 파일은 배포 책임자가 관리하고 배포한다. **TUI는 카탈로그를 내려받지 않는다.** 카탈로그를 머신에 가져오는 방법(스크립트, 수동 복사, 릴리스 첨부 파일)은 TUI 밖의 일이다.
- TUI는 카탈로그마다 다음 순서로 찾고, 처음 찾은 것을 쓴다.
  1. 환경변수 `AGENT_HARNESS_WIKI_CATALOG`, `AGENT_HARNESS_SKILLS_CATALOG`, `AGENT_HARNESS_DOCS_CATALOG`에 지정한 경로. 상대 경로는 프로젝트 루트 기준이다.
  2. 실행 파일 옆의 `catalog/<kind>.json`
  3. 이 저장소의 `catalog/<kind>.json`을 실행 파일에 내장한 샘플
- 배포물은 실행 파일 하나다. 카탈로그 파일은 선택 리소스다.
- 모르는 키, 맞지 않는 `kind`, 지원하지 않는 `schema_version`, 중복 `id`가 있는 파일은 거부하고 오류를 보여 준다. 다른 카탈로그로 몰래 대체하지 않는다.
- 카탈로그마다 출처(경로 또는 "내장 샘플")와 `catalog_version`을 보여 준다.
- CI는 내장 샘플을 TUI와 같은 Rust 타입으로 파싱해 검사한다.

## 2. 위키 카탈로그

- 각 항목은 Wiki.js 페이지를 `uuid`와 경로 `type`(예: `skill`, `claude/hook`)으로 가리킨다. type은 JSON에 적고, TUI가 추론하지 않는다.
- `target`이 TUI의 처리를 정한다.
  - `skill`: 게이트웨이 API v2(`GET /api/v2/documents/<uuid>?type=<type>`)로 받아 1단계와 같은 방식으로 `.skills/<id>/`에 가져온다. `SKILL.md`/`SKILL_ko.md`로 저장하고, 부분 가져오기는 동의한 경우에만 하며, `contentHash`를 `harness.lock.json`에 기록한다.
  - `doc` 또는 값 없음: 목록에만 표시한다.
- `status: "archived"` 항목은 보관됨으로 표시하고 가져올 수 없다.
- UUID는 소문자로 맞춰 비교한다.
- 게이트웨이 토큰은 선택 사항이다. 사용자는 TUI에서 토큰을 입력할 수 있고, 토큰은 Git이 무시하는 `.harness/local.toml`에 저장된다. 토큰이 없어도 읽기는 진행하고, 401/403이면 토큰을 요청한다. 토큰 값은 화면, 미리보기, 로그에 표시하지 않는다. `token_env`가 가리키는 변수에 토큰이 있으면 저장된 토큰보다 우선한다.
- 2단계가 아닌 백로그: 스킬이 아닌 페이지의 dynamic(사용할 때 받기)·static(영구 저장) 방식.

## 3. 공개 스킬 카탈로그

- 설치는 공식 skills CLI인 `npx skills add`(vercel-labs/skills)로만 한다. `npx`만 쓰고 다른 패키지 실행 도구는 제공하지 않는다.
- **사용자가 확인한 뒤에만 TUI가 설치를 실행한다.** TUI는 무엇을 설치할지만 정한다. 나머지는 skills CLI가 맡고 사용자에게 직접 묻는다: 대상 에이전트, project·user 범위, 설치할 스킬 선택, `source`에 적힌 버전.
- 명령은 항목의 구조화된 필드로 만든다. 카탈로그의 명령 문자열을 그대로 쓰지 않고, `-a`, `-g`, `-y`를 붙이지 않는다.

  ```text
  npx skills add <source> [-s <skill>]
  ```

  `skill`이 없거나 `*`이면 `-s`를 넘기지 않는다.
- 셸 없이 인자 배열로 실행하고, 작업 디렉터리는 프로젝트 루트다. Windows에서는 `npx.cmd`를 실행한다. 스크립트 파일은 만들지 않는다.
- 확인 전에 이름 충돌을 검사한다: `npx skills add <source> -l`로 설치 없이 스킬 이름 목록을 받는다. 설치될 이름(항목의 `skill`, 전체 설치이면 목록의 모든 이름) 중 하네스가 이미 배포한 스킬과 같은 것이 있으면 충돌로 표시하고 설치를 실행하지 않는다. `-l` 출력 형식은 구현할 때 공식 문서로 확인한다. 이름을 확실히 읽을 수 없으면 추측하지 않고 검사를 사용 불가로 표시한다.
- 확인 화면에 명령 전체를 보여 준다. 확인하면 TUI는 raw 모드와 대체 화면에서 빠져나와 터미널을 CLI에 넘긴다(stdin·stdout·stderr 상속). CLI의 질문은 사용자에게 바로 전달된다. CLI가 끝나면 TUI는 Enter를 기다린 뒤 화면을 복원하고 종료 코드를 보여 준다. 0이 아닌 종료 코드는 실패이며 성공으로 표시하지 않는다.
- `npx`를 찾지 못하면 설치 기능을 사용 불가로 표시한다.
- 설치 위치와 링크 방식은 skills CLI가 정한다. 하네스는 그 파일의 소유권을 갖지 않는다.
- `installer`가 `skills-cli`가 아닌 항목(예: `claude plugin`)은 `install` 문구를 보여 주기만 하고, 실행은 사용자가 한다.

## 4. 문서 카탈로그

- 2단계에서는 문서 항목을 목록으로만 보여 준다.
- 2단계가 아닌 백로그: TUI가 문서를 `references/<filename>`에 내려받는다. `sha256`이 없으면 경고하고 진행한다. `sha256`이 있는데 일치하지 않으면 그 파일은 저장하지 않고 경고한다.

## 5. TUI

- 카탈로그 화면을 추가한다. 세 카탈로그와 각 출처·버전, 항목별 상태(사용 가능, 가져옴, 보관됨, 충돌, 사용 불가)를 보여 준다.
- 위키 스킬 가져오기는 기존 미리보기·적용 흐름을 거친다. 스킬 설치는 명시적인 확인 화면에서만 실행한다.
- 카탈로그가 없을 때의 1단계 동작(수동 UUID 입력, 로컬 디렉터리 소스)은 그대로 유지한다.

## 6. 완료 기준

- 1단계 완료 기준을 모두 계속 충족한다.
- 카탈로그 파일이 없으면 내장 샘플을 읽고, 카탈로그를 읽기 위한 네트워크 요청을 하지 않는다.
- 환경변수 카탈로그와 실행 파일 옆 카탈로그가 정한 순서대로 우선하고, 화면에 어떤 것을 쓰는지 표시한다.
- 잘못된 카탈로그(모르는 키, 틀린 `kind`, 미지원 버전, 중복 `id`, 옵션처럼 보이는 `source`·`skill`)는 오류를 보여 주며 거부한다.
- `target: "skill"`인 위키 항목은 게이트웨이 API v2로 가져오고 `contentHash`를 기록한다. 다른 항목은 가져올 수 없다.
- 게이트웨이는 토큰 없이 동작한다. 저장된 토큰은 전송되지만 표시되지 않고, 추적 파일에 기록되지 않는다.
- 스킬 설치: `skill`이 있을 때와 없을 때의 인자 배열이 정확하고, `-a`, `-g`, `-y`가 들어가지 않는다. 확인 없이는 실행하지 않는다. 종료 코드를 보고한다. `npx`가 없으면 사용 불가로 표시한다. 하네스 배포와 이름이 겹치면 실행을 막는다. 테스트는 실제 CLI 대신 대체 실행 파일을 쓰고, CLI와의 대화 과정은 수동으로 확인한다.
- 영문·한국어 문서가 같은 내용을 유지한다.

## 산출물

애플리케이션 변경, `catalog/` 아래 내장 샘플 카탈로그, 관련 테스트, 영문·한국어 사용 문서, 카탈로그 규약.
